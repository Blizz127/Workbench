# Workbench

Workbench is a **standalone, reusable local project-state dashboard** for
AI-assisted software, reverse-engineering, and preservation projects.

It is **not** part of Xenogears, TEN, or any one project. It is the tool that
sits *above* them: a mission-control desktop app that tracks where each of
your long-running projects stands — progress, frontiers, blockers, builds,
tests, notes, and handoffs — so that you (or an AI assistant you paste context
into) can pick any project back up in seconds, even after months away.

Repository: `Blizz127/workbench` · Cross-platform (.NET 9 + Avalonia, Windows
and Linux) · All data stays local in SQLite.

---

## 1. What Workbench does

- **Project dashboard** — every registered project as a card: status
  (Active / Waiting / Broken / Research / Complete), repository path, current
  branch, last commit, last build result, last test result, current frontier,
  active task, last updated. Filterable by status.
- **Project details** — recent commits, git status, modified files, ahead/behind
  the upstream branch, a `diff --stat`-style summary and `diff --check`-style
  warnings, open TODO/FIXME comments scanned from the source tree, frontiers,
  blockers, recent notes, current milestone and objective (see §5).
- **Progress tracking** — milestones (visual checklist), frontiers
  (current / next / completed) with the full detail a handoff needs — exact
  symbol, evidence, blocker class, next safest step, assigned model — plus
  blockers (open / resolved with resolution text). Everything survives restarts.
- **Timeline** — an append-only engineering journal per project
  (`Build succeeded`, `Implemented func_800248D4 opcode 0xB3`,
  `Render crash resolved`, …). Build, test, refresh, and regression events are
  journaled automatically; anything else you add by hand.
- **Notes** — free-form markdown notes, searchable.
- **Handoff, checkpoints, and model prompts** — a generated markdown summary
  of current state, a preview-then-confirm way to append a checkpoint into the
  project's own repo, and a separate button that assembles a task-focused
  prompt from frontier, last failure, log findings, rules, and git status
  (see §6).
- **Build / run / test / matching-build / custom command execution with
  history** — run any of the project's configured commands from the app and
  keep an append-only record of every invocation, with automatic scanning for
  known failure signatures (see §7).
- **GitHub sync** — explicit, button-driven Fetch, Pull (fast-forward only),
  and Push actions for keeping a repository in sync across machines, each
  guarded by a safety check and recorded to the timeline (see §7.5).
- **Tags and global search** — search spans projects, notes, milestones,
  timeline entries, and frontiers.

## 2. What it does NOT do (yet)

Being explicit, because the name "AI-assisted" invites assumptions:

- **No AI provider integration.** Workbench does not call Claude, GPT, or any
  other model. There is no chat, no API key, no prompt sent anywhere. The
  handoff document and the model prompt are both generated by plain
  rule-based code and leave the app only when *you* copy or confirm them.
- **No automatic code modification.** Workbench never edits, patches, or
  commits your project's source. It reads git state, runs the commands you
  configured, and — only on your explicit confirmation — appends a checkpoint
  note to one fixed file, `docs/ai_context/ACTIVE_HANDOFF.md`, inside the
  project's own repo (the same category of action as exporting
  `workbench.json`: a Workbench-owned context artifact, not source code).
  Workbench never stages or commits anything on your behalf.
- **Git writes are explicit, narrow, and confirmed.** The only git commands
  Workbench ever runs against a remote are `git fetch`, `git pull --ff-only`,
  and `git push` — each behind its own button, each gated by a safety check
  that can block it outright, and Pull/Push additionally require a preview-
  then-confirm step (see §7.5). Workbench never auto-commits, auto-stashes,
  auto-merges, auto-rebases, force-pushes, or creates remotes/branches on its
  own.
- **No agent orchestration, no API-backed prompt pipelines.** Prompts are
  assembled as text for you to paste; nothing is sent anywhere automatically.
  That remains a later phase (see the roadmap in §8).
- **No sync or hosting.** State lives in a local SQLite database
  (`~/.config/Workbench/workbench.db` on Linux, `%APPDATA%\Workbench` on
  Windows; override with `WORKBENCH_DATA_DIR`). Nothing is uploaded.

## 3. Creating or importing a project

```bash
dotnet run --project src/Workbench.App
```

On first launch a sample project (Xenogears Decompilation) is seeded so every
screen has something to show. A second tracked project (Parasite Eve
Decompilation — parked, early disc-verification phase) is seeded whenever it
is missing. To add your own:

1. **Dashboard → “+ Add project”.** Give it a name, a repository path, or both.
   The path can be any local git clone — decomp tree, server emulator,
   ordinary software project.
2. **Import happens automatically.** If the repository root contains a
   `workbench.json` (see §4), its configuration — commands, docs paths, tags —
   is adopted on registration.
3. **Refine in Settings.** Each project's Settings tab edits status,
   description, tags, repository path, build/run/test/matching-build
   commands, documentation paths, AI context paths, and model prompt rules,
   and can export/import `workbench.json` at any time.
4. **Set your first frontier.** On the Overview tab, type the thing you are
   currently pushing on (a function address, a protocol message, a subsystem)
   and hit *Advance*. Fill in the exact symbol, evidence, blocker class, and
   next safest step as you learn them — that detail is what makes a handoff or
   model prompt actually useful later.

Deleting a project (Settings → danger zone) removes it and its history from
Workbench only — your repository is untouched.

## 4. How `workbench.json` is intended to work

Each project can carry a `workbench.json` at its repository root, so the
project's *operational* configuration travels with the code instead of living
only in one machine's database:

```json
{
  "name": "Xenogears Decompilation",
  "description": "Decompilation of Xenogears (PSX) toward a native PC port.",
  "buildCommand": "./pc_port/build_port.sh",
  "runCommand": "./build/xenogears",
  "testCommand": "python3 tools/check_matches.py",
  "matchingBuildCommand": "make -B build",
  "documentationPaths": ["docs/", "notes/memory-map.md"],
  "aiContextPaths": ["docs/decomp-guide.md", "include/"],
  "promptRules": "Never modify original decomp source under asm/ or src/ without matching evidence.",
  "customLogPatterns": [
    { "name": "RUN_RC=", "pattern": "RUN_RC=", "isRegex": true, "category": "TestHarness" }
  ],
  "tags": ["Reverse Engineering", "Game Preservation", "PSX"]
}
```

- **Registering a repo that has one** imports it automatically.
- **Export/Import buttons** in Settings write/re-read it, so you can edit
  either in the app or in a text editor and keep the two in sync.
- `documentationPaths` point at the docs a human should read first.
- `aiContextPaths` point at the files an AI assistant should be given as
  context when you hand a task over (nothing reads them automatically today —
  they are the declared inputs for the later prompt-export phases).
- `matchingBuildCommand` is a build invoked specifically to check match or
  regression status, kept separate from the everyday build command.
- `promptRules` is free text included verbatim in the generated model prompt.
- `customLogPatterns` teaches the log-finding scanner this project's own
  markers, merged with the built-in generic toolchain/crash patterns.
- `preferredAiProvider` is an optional reserved field for later phases; it
  does nothing yet.
- **Scope note:** `workbench.json` round-trips the fields above, but not a
  project's *custom commands* (the open-ended list beyond build/run/test/
  matching-build) — those are configured once through the Builds & Tests tab
  and persist from then on.

Commit `workbench.json` to the project's repo like any other config file.
Sample configurations for four project shapes live in [`samples/`](samples/).

## 5. Refresh Project: real local state, not a cache

The Overview tab's **↻ Refresh Project** button reads your repository as it
actually stands right now — branch, HEAD, commits ahead/behind the upstream
tracking branch, dirty status, a `diff --stat`-style summary, and a
`diff --check`-style scan for trailing whitespace and unresolved conflict
markers. Nothing here is destructive; it only reads.

What makes it more than a status readout: Workbench remembers what it saw
last time (on the project itself — branch, HEAD, dirty flag, ahead/behind), and
when a refresh finds something **meaningfully different** — a new commit, a
branch switch, the tree going from clean to dirty, a change in how far ahead
or behind you are — it journals exactly that to the timeline. Diff stat and
diff-check warnings are always shown but not journaled on every refresh; they
supplement the headline state rather than replace it. The first-ever refresh
of a project journals a single baseline entry instead of a diff, since there's
nothing yet to compare against.

## 6. Handoff, checkpoints, and model prompts

Every project has a **Handoff** tab with three related but distinct outputs —
none of which involve an AI provider:

- **Handoff document** — the same rule-based markdown summary as Phase 1:
  current state, last completed work, open blockers, and a recommended next
  step. *Copy to clipboard* and paste it wherever you're working.
- **Append Handoff Checkpoint** — writes that same content, wrapped with a
  timestamp, into `docs/ai_context/ACTIVE_HANDOFF.md` inside the project's own
  repository. This always goes through a **preview step**: clicking the
  button shows you exactly what will be appended, and nothing is written
  until you hit *Confirm & Append* (or discard it with *Cancel*). The file is
  append-only — existing entries are never rewritten or removed — and
  Workbench never runs `git add` or `git commit` on your behalf.
- **Generate Model Prompt** — a separate, more targeted document: the current
  frontier's full detail, the most recent failing command (across build/run/
  test and any matching-build/custom command) with a bounded log excerpt, the
  log findings detected in that failure, the project's prompt rules, and
  current git status (branch, ahead/behind, files changed, diff stat). It has
  its own *Copy to clipboard* button. This is text assembly only — nothing is
  sent anywhere; you decide where it goes.

The quality of both outputs depends entirely on the journal: the more
faithfully you record frontiers, blockers, and timeline entries, the better
the pickup — for a human or for whatever you paste the prompt into.

## 7. Command execution, history, and log findings

Each project has four fixed command slots — **build**, **run**, **test**,
**matching-build** — plus an open-ended list of **custom commands** you name
yourself (a targeted repro, a symbol diff, a packet-capture replay). Configure
them in Settings, `workbench.json`, or directly on the Builds & Tests tab.

- Commands execute via the platform shell (`cmd.exe` / `/bin/sh`) in the
  repository directory, with stdout/stderr captured interleaved and a
  timeout. A running command can be cancelled from the UI; cancellation kills
  the whole process tree and the attempt is recorded like any other outcome.
- Every invocation is stored **append-only**: command, timestamp, exit code,
  duration, output log, and the HEAD commit (and dirty status) it ran
  against. History is never overwritten — a decomp's build log from three
  months ago is evidence, not clutter. Logs are capped at capture time (the
  first and last ~200 KB are kept, with a marker noting what was dropped), so
  a runaway command can't bloat the database; list views load logs lazily,
  only for the run you select.
- Each run also journals a timeline entry automatically (with the tail of the
  output attached on failure).
- **Regression detection:** if the previous run of that *same* command
  (matched by name) succeeded and this one fails — or a previously passing
  test suite stops passing — Workbench journals a `Regression` timeline entry
  and flags the record itself. Timeouts count as failures; a cancel you
  triggered yourself does not.
- **Log findings:** every stored output log can be scanned for known failure
  signatures — built-in generic patterns (`undefined reference`,
  `multiple definition`, `relocation truncated`, `SIGSEGV`, `Aborted`,
  `assert`, …) plus whatever a project declares in `customLogPatterns`. Matches
  show the line number, category, and matched text, and feed directly into the
  generated model prompt.

Test results are recorded as Passed / Failed / Error / TimedOut, with optional
notes (e.g. `1042/1893 functions matching (55.0%)`) and the associated commit.

## 7.5. GitHub sync: Fetch, Pull, Push

For projects you work on from more than one machine, the Overview tab has a
**GitHub** card with three explicit actions. Nothing here runs on its own —
every action is one button click, and Pull/Push additionally show a preview
of exactly what will happen before a **Confirm** button does anything:

- **⇅ Fetch/Update from GitHub** — runs `git fetch --all --prune` and
  refreshes the branch/ahead/behind/dirty state shown on the card. This is
  always safe to run: a fetch never touches your working tree or history.
- **⏩ Pull (fast-forward)** — appears only once a fetch shows the branch is
  behind. Runs `git pull --ff-only`, and only if:
  - the working tree is clean (a dirty tree blocks the pull with a warning
    telling you to commit or discard first — Workbench will not stash for
    you), and
  - the branch hasn't diverged (if it's both ahead and behind, Workbench
    blocks the pull and tells you to resolve it manually — no automatic
    merge or rebase, ever).

  Because `--ff-only` is passed to git itself, even in the small window
  between the check and the command, git will still refuse and no local
  state changes.
- **⬆ Push committed changes** — appears once the branch is ahead of
  upstream. Runs `git push`. A dirty working tree does not block the push —
  only what you've actually committed goes — but the preview and the result
  both warn you that uncommitted changes are being left behind. If no
  upstream is configured, Push is blocked with a message telling you to set
  one yourself (`git push -u origin <branch>`); Workbench never creates a
  remote or branch on your behalf.

Every fetch/pull/push attempt — blocked, succeeded, or failed — is journaled
to the timeline (category `GitSync`) with the command, branch, HEAD before/
after, and ahead/behind before/after, so the history of what was synced and
when is preserved alongside everything else.

**One nuance worth knowing:** Pull's ahead/behind check reads whatever the
last fetch (or Refresh Project) recorded — it does not implicitly fetch for
you first. If origin has moved since your last fetch, run **Fetch/Update**
before trusting the Pull button's availability or the numbers on the card.

## Example projects

[`samples/`](samples/) contains `workbench.json` examples for five shapes of
project:

| Sample | Shape |
|--------|-------|
| [`samples/xenogears/`](samples/xenogears/) | **Xenogears Decomp / PC Port** — matching decompilation with a match-rate test harness, a matching-build command, and project-specific log patterns. |
| [`samples/parasite-eve/`](samples/parasite-eve/) | **Parasite Eve Decomp** — an early-phase decomp still in disc verification/setup: no build or matching commands yet, parked behind Xenogears. |
| [`samples/ten-revival/`](samples/ten-revival/) | **TEN Revival** — bringing a dead online-game network back: protocol RE, relay/lobby server. |
| [`samples/crimson-sands/`](samples/crimson-sands/) | **Crimson Sands / D&D server revival** — MMO server emulation from packet captures. |
| [`samples/generic-software/`](samples/generic-software/) | **Generic software project** — any ordinary codebase with build/test commands. |

Workbench treats all four identically — it is project-shape agnostic. The
frontier for a decomp might be a function address; for a server revival, a
packet opcode; for ordinary software, a feature.

## 8. Roadmap

| Phase | Scope | Status |
|-------|-------|--------|
| **1** | Local dashboard, progress/frontier/blocker model, timeline journal, notes, milestone tracking, handoff document, SQLite persistence. | ✅ this repo |
| **2** | Execution/history hardening and real local project state: capped log capture, lazy log loading, UTC timestamps, cancellable commands, live git refresh (ahead/behind, diff-stat, diff-check) with change journaling, matching-build/custom commands with their own append-only history and regression detection, log-pattern scanning, a rich frontier editor, handoff checkpoints, and model prompt assembly. | ✅ this repo |
| **3** | AI handoff / prompt export hardening: richer context-bundle packaging (the files named in `aiContextPaths`, not just their paths), saved prompt presets. Still no API calls — export only. | planned |
| **4** | Optional provider integrations: pluggable modules (Claude, GPT, local models, …) that can *receive* the assembled prompt and report results back. Strictly optional; Workbench never depends on any one provider, and nothing runs without explicit user action. | planned |
| **5** | Multi-project cockpit / boss dashboard: cross-project priorities, "what should I work on right now" across the whole portfolio, aggregate regression and staleness views. | planned |

At every phase the invariant holds: Workbench records and reports; it does not
autonomously modify your projects' source code.

## Getting started / development

Requirements: [.NET 9 SDK](https://dotnet.microsoft.com/download/dotnet/9.0).

```bash
git clone https://github.com/Blizz127/workbench
cd workbench
dotnet run --project src/Workbench.App   # run the app
dotnet test                              # run the test suite
```

| Project | Purpose |
|---------|---------|
| `src/Workbench.Core` | Domain models and service contracts. No external dependencies. |
| `src/Workbench.Data` | SQLite persistence: schema migrations, repositories, search. |
| `src/Workbench.Git`  | LibGit2Sharp-backed git snapshotting and TODO scanning. |
| `src/Workbench.App`  | Avalonia UI (MVVM via CommunityToolkit.Mvvm). |
| `tests/Workbench.Tests` | xunit tests for the data layer and core services. |
